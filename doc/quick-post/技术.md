# 快速发帖（quick-post）技术方案 v8

状态：已评审（v8，2026-10-24 用户确认发帖文案口吻与格式调整）。配套文档：[需求.md](需求.md)、[原型/index.html](原型/index.html)。

## 入口与界面分离（v5，2026-10-24 确认并实施）

- **工具栏 popup 双入口**：「打开回复面板」发 `OPEN_QUICK_REPLY`，「发帖助手」发 `OPEN_QUICK_POST`；页面脚本按消息类型与场景严格配对，错配时明确报错（发帖场景拒绝打开回复面板，非发帖场景拒绝"发帖助手"），不共用入口或面板 Tab。
- **页面面板按场景独立**：回复/私信场景只渲染回复面板（含一键回复倒计时）；发帖场景只渲染发帖面板（缓存池），互不包含对方组件。
- **设置页双 Tab**：「回复」（候选数量、回复提示词、回复示例、自动点赞、一键回复、倒计时）与「发帖」（发帖提示词、发帖示例）分开；网关 URL 与默认语气为共用项置于 Tab 之上；保存一次写入全部。
- 版本 0.6.0；一键回复（issue-14）与发帖共存于同一分支（feat/issue-14-one-click-reply 已合并入 feat/quick-post）。

版本演进：

- v2（2026-10-23）：决策前移到话题候选，帖文基于确认话题生成。
- v3（2026-10-24）：话题从 xzhishu 热榜取 5 条决策定 1 条、无手动输入；只进草稿；只要回填不要复制。
- v4（2026-10-24 用户反馈）：**每次只发一条，其余候选缓存待下次使用，可换选**。新增候选缓存池（持久化）与换选规则。

v4 流程：**xzhishu 热榜前 5 条 → 百炼 choice 定 1 条 → 生成 5 条帖文入缓存池 → 每次从池中选 1 条回填草稿 → 人工点击发帖；未用候选留池待下次**。

本文区分三类信息：**事实**、**推测**、**待验证**（定义同前版）。

## 1. 证据来源

事实：

- 现有架构：Chrome MV3 扩展 + 本地 Python 网关；生成 → 百炼 choice → 回填草稿 → 人工发送。依据：`../技术.md`。
- 现有网关契约 `quick-reply.v2` 与错误码 400/403/503/502/504；`extension/src/settings.js` 现有设置项；manifest 权限（`storage`、`scripting`）。依据：2026-10-23 读取源码与文档。
- 现有回复流程"不支持普通发帖"；回复候选与对话"仅内存处理，不写 chrome.storage"是现行隐私边界。依据：`../需求.md`、`../技术.md`。**v4 对发帖候选破例持久化，见第 8 节。**
- xzhishu 热榜（2026-10-23 实测）：页面标注"每 10 分钟自动更新"、页脚标注"API（暂未开放）"；前端数据接口 `GET /api/v1/topics/hot?limit=&period=&dimension=&detail=` 可匿名访问，返回话题数组（id/rank/title/summary/heat/…/repliesCount/tags/sourceTweets）。字段与参数取自其前端代码，非官方文档。
- 2026-10-23 实测热榜前 5 条：A股跌破3600点资金出逃、币安推出 Agentic Wallet 功能、比特币纳指下跌时表现坚挺、SpaceX 发行高息债券引关注、iPhone Duo 内屏膜被指为出厂贴膜。
- 用户 2026-10-24 决定：接入 xzhishu、只进草稿、只要回填；以及候选缓存与换选（本次 v4）。
- 0.3.0 先例：设置存储失败必须显示失败，不能提示已保存（缓存写入同此规则）。

推测（实现前复核）：

- 发帖编辑器同为 `tweetTextarea_*` contenteditable，可复用单次 paste 写入与精确核验；compose 弹窗判定可沿用"弹窗边界 + 唯一编辑器"思路。
- 百炼 choice 可用于 5 选 1 话题筛选；帖文 ≤280 字符按中文普通帖容量取值。
- chrome.storage.local 可满足缓存持久化（存储容量与 schema 校验实现时复核）。

待验证：

- xzhishu 接口的持续可用性、字段稳定性、频率限制与条款合规性（未授权第三方源；**接入决定由用户 2026-10-24 做出，风险确认仍待回复**）。
- `period/dimension/detail` 参数精确行为；真实 X 发帖框 DOM 与弹窗区分；生成质量与真实互动效果（人工观察）。

## 2. 架构与模块边界

| 模块 | 新增职责 | 边界 |
| --- | --- | --- |
| `extension/src/content.js` | 发帖场景识别；发帖面板 UI：缓存池列表（选用/换选/删除/清空）、"生成新一批"；候选"填入发帖框" | 回填沿用空草稿、单次写入、精确核验、owned 替换；无复制按钮；绝不点击发帖按钮 |
| `extension/src/service-worker.js` | posts 编排：路由校验 → 榜单获取 → 决策 → 帖文生成 → 入缓存；选用/换选/删除/清空的缓存编排 | 任一步失败不执行后续；不重试、不自动追加调用；缓存读写失败显式报错 |
| `extension/src/settings.js` | 新增 `postPrompt`（必填，1–3000）、`postExamples`（可选，≤3000） | 机制同 `replyPrompt` 0.3.0 |
| `gateway.py` | `POST /v1/posts/topics/fetch`、`/v1/posts/topics/decide`、`/v1/posts/generate`；榜单获取在网关侧 | 数据源固定 xzhishu，不切换、不缓存备用；网关不保存候选 |
| `prompts/post-policy.md` | 选题节 + 帖文节共同质量标准 | 缺失/为空直接失败 |

网关不参与缓存：缓存池只存在扩展 `chrome.storage.local`，网关仍是无状态的获取/决策/生成。

## 3. 关键流程（v4）

**生成新一批**（面板按钮，一键完成三步，失败按阶段停止）：

1. 网关请求 xzhishu 热榜（`limit=5&period=24h&dimension=heat&detail=1`），严格解析，取前 5 条的 `id/title/summary/tags/repliesCount`（`sourceTweets` 不传给模型）。
2. 百炼 choice 从 5 条话题定 1 条（可 `__none__` 拒选，拒选即停止）。
3. 生成恰好 5 条帖文 + 核实提示，写入缓存池；面板显示"本批话题：…，5 条已入池"。

**选用与换选**（每次只发一条）：

4. 缓存池列表按生成时间倒序展示（文本、核实提示、来源话题、时间、已发标记）；点"填入发帖框"选 1 条写入空草稿。
5. 填入成功的条目打"已发过"标记（灰化、不可再次填入），并在"当前草稿来源"行显示（带"放回缓存"按钮，可撤销标记）。
6. 换选：再填入其他条目时，当前条目自动撤销标记放回可选（不丢失），新条目写入草稿（owned 替换规则）；用户手动改过草稿则不替换、报"草稿已变化"。
7. 人工点击 X 发帖按钮发布；插件不感知发帖完成。"已发过"标记跨会话保留，达到上限时按第 4 节规则清理。
8. 条目可单条删除、可清空；删除/清空即时持久化。

单次生成新一批 = 一次榜单获取 + 一次决策 + 一次生成；选用/换选不调用模型。

## 4. 接口与数据契约

网关契约与 v3 相同（`schemaVersion: "quick-post.v1"`）：`/v1/posts/topics/fetch`、`/v1/posts/topics/decide`、`/v1/posts/generate`；错误码 400/403/503/502/504 含脱敏 `error` 与失败阶段。生成响应固定 5 条 `{id, text≤280, checkNotes[]}`。

**缓存存储契约（扩展侧，chrome.storage.local）**：

```json
{
  "quickPost.cache.v1": {
    "items": [
      {
        "id": "uuid",
        "text": "帖文正文",
        "checkNotes": ["…"],
        "sourceTopic": { "id": "…", "title": "…" },
        "batchId": "uuid",
        "createdAt": 0
      }
    ],
    "limit": 30
  }
}
```

- 读取时严格校验结构，损坏或读取失败明确报错，**不得当作空缓存**。
- 写入失败明确报错（阶段 `cache.write`），本批候选标注"未入缓存"，不提示已缓存。
- 条目可含 `usedAt`（填入成功后打"已发过"标记）：灰化、不可再次填入；换选或"放回缓存"撤销标记；标记跨会话保留，作为不重复发的历史（2026-10-24 评审结论）。
- 上限默认 30 条（常量，不是设置项）；达到上限（含本批入池后超出）时自动清理：**先删除已发过的条目，再按 createdAt 删除最旧条目**，直至可容纳；清理条数在状态区可见提示。

## 5. 发帖框识别与回填

- 目标：`/compose/post` 路由的发帖编辑器，或当前页唯一 compose 弹窗内唯一发帖编辑器且无被回复目标帖；歧义即停。
- 回填复用回复 0.2.8 机制：仅写空草稿 → 单次 paste → 150ms 精确核验 → owned 标记；失败即停不重试。
- 换选时仅当草稿仍是完全未修改的插件草稿才允许替换；用户改动后停止替换并报"草稿已变化"。
- 无复制按钮；面板无发帖按钮（只进草稿）。

## 6. 提示词

`prompts/post-policy.md` 分为选题节与帖文节：选题 criteria 保持适合展开、事实可核实、全部不合适必须 `__none__`；帖文优先学习用户自己的直接提问、补充判断、自然追问和短段落分行，不强制钩子、问题句、评论区号召或固定行数。`postPrompt`/`postExamples` 仍由用户可编辑，示例用于学习句式、分行、口语标点和追问节奏，不作为当前事实。

## 7. 依赖与配置

- 复用现有 LLM_* 与百炼配置，无新增配置项；缺失 503 停止。
- 数据源固定 xzhishu 热榜常量；无备用源、无内置话题、不用旧榜单替代。
- 无新增依赖；缓存上限 30 为代码常量。
- 升级行为默认：老用户升级后 `postPrompt` 缺失时写入显式默认值（同 0.3.0 先例，待评审确认）。

## 8. 权限与隐私

- 不新增 Chrome 权限（xzhishu 获取在网关侧；`storage` 权限已存在）。
- **持久化边界变更（用户 2026-10-24 明确要求）**：发帖候选缓存写入 `chrome.storage.local`（文本、核实提示、来源话题标题、时间戳）；这是对现行"候选仅内存"边界的破例，仅限发帖候选；**回复候选与对话仍仅内存**。缓存不进日志、不进仓库、不上传第三方；扩展卸载即清。
- 榜单查询不携带用户内容；选定话题标题/摘要与两个模型服务商共享（同现有声明）。
- **第三方数据源风险（待用户明确确认）**：xzhishu 官方 API 标注未开放，本集成使用其页面数据接口，属未授权第三方源，存在条款/合规/稳定性/限流风险；失效即显式报错停止，不换源。使用前建议自行核对其服务条款。
- 候选是模型输出，不保证事实正确；插件不自动发帖。

## 9. 错误与停止条件

失败即停、暴露阶段与原因，禁止兜底/降级/重试。失败阶段：`topics.fetch`、`topics.fetch.parse`（含 0 条）、`config`、`topics.decide.parse`、`topic.unselected`、`posts.parse`、`cache.read`、`cache.write`、`route.changed`、`target.ambiguous`、`fill.draft`、`fill.paste`、`fill.verify`。缓存读失败 ≠ 空缓存；缓存写失败 ≠ 已入池。任何一步失败不执行依赖它的后续操作。

## 10. 测试与真实验收边界

- 自动化：JS 单测覆盖场景识别、缓存入池/出池/换选放回/删除/清空、持久化恢复、读写失败报错、上限提示、owned 换选与草稿变化停止、路由变化停止；Python 单测覆盖三端点契约、xzhishu 合成样本解析（明确标注测试替身）、0 条/非法结构报错、决策拒选、提示词加载失败。
- 真实验收（人工）：Chrome 已登录 X，`/compose/post` 与首页 compose 弹窗各验完整链路（含真实 xzhishu 请求成功一次）；跨会话缓存恢复；换选不丢条目；发布后观察互动。
- 合成 xzhishu 样本不代表真实接口可用；真实榜单请求须实际成功才算验证。

## 11. 上线与回滚

- 扩展 + 网关同版本发布（建议 0.6.0，**推测**）；更新后重载扩展并刷新 X 页面。
- 回滚：回退版本；缓存数据结构 `quickPost.cache.v1` 若未来变更需保留读取或显式迁移说明（当前无历史数据）。

## 12. 评审结论（2026-10-24）

1. **第三方数据源风险**：用户结论"就按照这样"——接受第 8 节所述风险边界与显式失败策略，xzhishu 接入按本方案实施。
2. **缓存上限与淘汰**：达到上限时**删除之前已发过的，然后删除最旧的**（自动清理，状态区可见提示）。
3. **选用计账**：按问题 2 的清理语义细化——已填入条目保留"已发过"标记（usedAt）直至被清理；换选或"放回缓存"撤销标记。若与用户预期不符，以用户后续纠正为准。
4. **生成新一批一键化**：同意（获取话题 → 决策 → 生成 5 条入池，失败分阶段停止）。
5. **缓存范围**：只缓存发帖候选；回复候选不缓存，仍仅内存。

沿用默认（用户未反对）：帖文固定 5 条一批；无手动输入；只回填不复制；只进草稿人工发帖；帖子类型仅引互动话题帖；帖文 ≤280 字符；面板"回复/发帖"双模式；`postPrompt` 缺失写默认值；决策不感知账号定位。

## 双榜单显式切换（v6，2026-10-24）

- `POST /v1/posts/topics/fetch` 请求体新增可选 `source`："topics"（默认，热门话题榜 `/api/v1/topics/hot?limit=5&period=24h&dimension=heat&detail=1`）或 "tweets"（热门推文榜 `/api/v1/rankings/tweets/leaderboard?period=24h&dimension=heat&page=1&pageSize=5`）。非法值 400。
- 推文榜条目在网关归一化为话题形状（title=正文前 120 字或文章标题，summary=正文/文章摘要 ≤2000，tags=分类，repliesCount=评论数）；素材超界的截断为有界取材，与私信 800 字符切片同例，帖文节要求重写不照抄。
- **切换只由用户显式触发**（面板"改用热门推文榜生成"按钮，或请求里的 source 字段）；任一榜单失败/为空即按其阶段报错并停止，不自动换源、不缓存旧榜单（符合"不得自动切换数据源"）。
- 面板主按钮与状态文案标明当前榜单（热门话题榜/热门推文榜）。真实验证（2026-10-24）：推文榜实取 5 条成功；话题榜为空按 `topics.fetch.parse` 显式失败。

## 每话题一条帖文 + 推荐 + 类别筛选（v7，2026-10-24）

- 流程：fetch（榜单 5 条）→ generate（**每话题各 1 条帖文**，candidates 携带 topicId 与话题一一对应）→ decide（**从帖文中推荐 1 条**，`best_post` choice，可拒选；拒选只隐藏推荐标记，帖文照常入池）→ 缓存入池（条目按 sourceTopic 分组展示）。
- 契约：`/v1/posts/generate` 请求为 `topics` 数组（1–5），响应 `candidates:[{id,topicId,text,checkNotes}]` 与话题一一对应；`/v1/posts/decide` 取代原 `/v1/posts/topics/decide`（对帖文 choice）。
- 类别筛选：`/v1/posts/topics/fetch` 请求新增 `categories`（类别名列表，来自设置页 11 类，2026-10-24 实测 /api/v1/categories）。仅热门推文榜支持（按条目 category 过滤后再取前 5）；热门话题榜遇类别筛选**明确报错**（不静默忽略）。
- UI：缓存池按来源话题分组（话题标题 + 其帖文卡片，卡片放大）；决策推荐条目标注"决策推荐"。
- **真实耗时发现（2026-10-24 实测）**：一次生成 5 条帖文实测约 43.6 秒，超过默认上游超时 25 秒（表现为 504 生成接口超时）。需在 .env 设置 `MODEL_TIMEOUT_SECONDS=60`（或以上，上限 90）；扩展侧总等待 100 秒不受影响。该值是显式配置，不是兜底。

## 用户口吻与发帖格式（v8，2026-10-24）

- 默认 `postPrompt` 以用户提供的历史发帖为主要风格证据：直接提问、补充自己的判断或观察、自然追问；允许连续几段记录式陈述作为另一种结构。
- 输出可使用 2–6 个短句行、2–4 个自然段和空行；不固定模板，不强制问题句，不机械添加“？？？”。
- “评论区聊聊”“报数”“站队”等固定互动话术不再作为默认要求；互动应来自帖文内容本身。
- 发帖提示词版本为 `post-policy.v2`；不新增模型、数据源、缓存或回填契约，真实模型质量与 X 页面效果仍待人工验收。
