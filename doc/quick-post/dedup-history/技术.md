# quick-post 重复帖文去重技术方案

状态：已按评审方案实现；自动化验证进行中，真实 X 验证未完成。

## 已确认事实、推测与待验证

已确认事实：`extension/src/service-worker.js` 的 `appendCache()` 读取现有 30 条缓存后直接追加生成候选；当前条目可用 `usedAt` 标记，但条目被淘汰后没有历史记录。网关当前只校验单批候选，不保存跨批状态。

合理推测：生成候选的 `text` 足以构成最低限度的重复判断；上游榜单的 `id` 若稳定，可作为来源级辅助指纹。

待验证：xzhishu 返回的 ID 是否跨刷新稳定；模型对同一主题的轻微改写是否应视为重复；500 条指纹在 `chrome.storage.local` 中的实际容量余量。

## 架构与数据契约

去重只在扩展 service worker 的缓存写入边界执行，网关无状态，不新增外部接口。保留现有 `quickPost.cache.v1`，新增独立键：

```json
{
  "quickPost.history.v1": {
    "version": 1,
    "items": [
      {"textHash": "sha-256", "sourcePostId": "optional", "firstSeenAt": 0}
    ],
    "limit": 500
  }
}
```

候选入池前计算：

- `textHash`：Unicode NFC、去首尾空白、连续空白折叠后的正文做 SHA-256；不删除标点，不做语义相似度推断。
- `sourcePostId`：仅当来源契约提供稳定 ID 时记录；缺失时为 `null`。
- 命中规则：`textHash` 已存在，或候选 `sourcePostId` 与历史记录相同，即判定重复。

## 流程

1. fetch → generate → decide 成功后，读取 `quickPost.history.v1`；读取失败立即停止，不写缓存。
2. 在 `appendCache()` 内按候选顺序去重：同批重复、历史重复均记录为 `skipped`，不进入 `items`。
3. 对实际入池的候选写入缓存与历史记录；两者写入必须作为一次明确的存储阶段处理。任一写入失败，返回失败并不宣称缓存成功。
4. 返回 `addedCount`、`skippedCount` 和脱敏原因计数（正文不写日志）；UI 显示“跳过 N 条历史重复”。
5. `usedAt`、放回、删除只操作缓存条目，不删除历史指纹。
6. 全部候选被跳过时停止并显示“本批无新候选；未重试、未换源”，不自动调用生成接口第二次。

## UI 原型对应行为

- 缓存池顶部显示“历史去重：已记录 X 条”和“清除去重历史”按钮。
- 批次成功状态显示新增与跳过数量。
- 清除历史需要二次确认，并明确会允许未来相同正文再次进入缓存；清除失败保持错误态。
- 空池状态区分“从未生成”和“本批全部重复”。

## 权限、隐私与错误停止

不新增 Chrome 权限；历史指纹与候选一样仅保存在本机 `chrome.storage.local`，不写日志、不上传网关。历史条目不保存完整正文，避免扩大持久化内容；调试复制信息不得包含哈希明文映射。

禁止自动重试、换模型、换数据源、用旧候选补足或静默忽略存储错误。异常必须保留 `cache.read`、`cache.write` 或 `cache.dedup` 阶段。

## 测试与真实验收边界

自动化测试：同批重复、跨批正文重复、来源 ID 重复、缓存淘汰后仍去重、放回不解除历史、删除不解除历史、读写失败、历史清除、全批命中停止、旧 `quickPost.cache.v1` 迁移。

真实验收：Chrome 重载扩展后生成相同或等价输入，确认已用帖文不再显示；不得把一次模型输出不同就当成“语义去重已验证”。

## 迁移、上线与回滚

首次读取不存在 `quickPost.history.v1` 时创建空历史，不回溯推断旧缓存是否已发过；可把现有缓存中有 `usedAt` 的条目写入历史（需在迁移日志中计数）。升级前备份本地扩展数据；回滚代码不删除历史键，旧版本忽略该键。
